# 交付总结：从"能用"到"能扛追问"的五个阶段

> 这份是给**作者本人**看的（不是给访客的）。按"简历/求职"口径整理：每个阶段做了什么、**实测数字**、
> 以及**哪些尝试被数据否决了**。可以直接抄进简历的版本在 [RESUME.md](RESUME.md)。

## 一句话

一个"哼开头几个音就能查到简谱"的站点：**11,495 首 / 2,532,332 音符**语料，
检索**全在浏览器里跑**（索引 5.12 MB gz → 31 MB 明文，就绪 ~200 ms，查询中位 ~106 ms），
写路径是"边缘反代 + 本机 git 提交"的混合架构 —— 在此基础上把**技术栈与工程质量**整体现代化了一遍。

## A. 说得清（术语、图、可复核的数字）

* `docs/ARCHITECTURE.md`：Mermaid 全链路图 + 组件职责 + **数据契约**（曲谱文件字段 / 索引字段 / 写接口四种载荷 / health 字段）+ 部署拓扑 + 瓶颈表。
* `docs/TECH_STACK.md`：分层选型（每项 **为什么选它 + 量化收益**）、**"刻意没用"清单**（DB/框架/打包器…各写清何时会引入）、**15 条难题 STAR 复盘**、**20 条面试 Q&A**。
* `tools/measure_stack.py` + `tools/bench_search.mjs`：把文档里引用的数字**实测出来**（可重跑）。
* `tools/check_docs_numbers.py`：四份文档里的曲数/音符数/小节线数/索引行数**必须与语料实测一致** —— 它当场抓到过"架构文档漏写小节线精确值"和我自己脚本的一个 bug。

**关键数字**：11,495 首 · 2,532,332 音符 · 552,836 显式小节线 · 11,991 份曲谱 · 平均 220 音符/首；
索引 5.12 MB gz → 31.01 MB（6.1×）；转写中位 38–61 s（59–95 份/小时）。

## B. TypeScript 化（前端三件 + 边缘 Worker）

* `static/jptok.ts`（词元口径）、`static/search.ts`（代价匹配与并列裁决）、`static/app.ts`（867 行主界面）、`worker/index.ts`（边缘路由/鉴权/注入）**全部 TS**；
  构建只用 `esbuild` 做**类型擦除**（不打包、零运行时依赖），`tsc` 三份配置（前端核心 strict / 主界面过渡 / Worker strict）进 CI。
* **零性能回退**：查询中位 151 → 139.9 ms（**这是 B 阶段当时的数**；E 阶段又优化到 ~106 ms）；主界面产物 46,449 → 33,605 B（-28%）。
* **顺手抓到 3 个"从来没跑过"的静默问题**：`buildIndex` 字段白名单漏了 `conf`/`confP10`（"置信度优先"这条并列依据一直形同虚设）、`app.renderScore` 从未 export（一条自检从写下就没通过过）、`check_tune` 的陈旧断言（字面量与 schema 化后的 DOM 不匹配）。

## C. 写后端迁 FastAPI + Pydantic v2 + uv（零口径重写）

* `app/api.py`：Pydantic v2 **discriminated union** 表达四种投稿载荷，自动产出 **OpenAPI/Swagger `/docs`**；业务规则**全部复用** `app/server.py`。
* **灰度对拍矩阵** `tools/check_parity_legacy_vs_fastapi.py`：21 条请求 × 三种鉴权场景（无口令/错口令/对口令）**全部一致**；对拍当场抓到 4 类差异，其中一处是**鉴权与解析的先后顺序**（安全语义）。
* 切换后在正式域名上真投稿成功（留档 + `git commit`）；`--impl legacy` 可随时退回标准库版。

## D. 工程质量门与可观测性

* **Prometheus `/metrics`**：请求计数用**归一化路径模板**（否则 1.1 万谱页会炸掉时间序列基数）、投稿结果按 `kind/result` 计数、语料规模 gauge 带 TTL 缓存；真语料实测 `corpus_songs 11495`，官方解析器校验 **14 个指标族**。
* **ruff + mypy 渐进门槛**（`tools/lint_python.py`，唯一真源）+ **pre-commit**（11 个钩子）+ `.gitattributes`（LF 定死，这个项目两次栽在 CRLF 上）。
* **Docker/Compose**（多阶段 + uv 锁 + 非 root + 健康检查；语料挂卷不烤进镜像）+ **GitHub Actions 三条流水线**（web node20/22 · python 3.11/3.13 · **docker build** —— 本机没装 Docker，镜像可构建性由 CI 证明）。

## E. 检索性能：两处真收益 + 一次被数据否决的尝试

| 项 | 实测 |
|---|---|
| **排序键预计算**（上线 ✓） | 排序比较器每次比较都现算 `versOf()`（内部 `new Set`）→ 改成每候选算一次键：**144.6 → 105.9 ms（-27%）** |
| **ngram 剪枝**（上线 ✓） | 4-gram 倒排 + **可证明安全**的采用条件（每段都能精确命中 且 代价 0 的结果够填满榜单，否则退回全扫）：长查询 **69.1 → 48.2 ms/条（-30%）**，60 条查询**结果逐条相同**；索引建在空闲时（~136 ms） |
| **Rust→Wasm**（**否决** ✗） | 0.9 KB、零依赖、不用 wasm-bindgen；逐首对拍 **137,940 次**比较代价全一致、端到端 15 条结果逐条相同 —— 但**端到端 0.84×（更慢）**，不带上线 |

**这一阶段最值钱的不是那两个百分比，而是两条纪律**：
① **先量再改** —— 我原以为瓶颈是"全库匹配扫描"，花了两轮去优化它；真瓶颈在排序比较器。
② **测试装置自己也会骗人** —— 对拍脚本、冒烟测试、覆盖率脚本，我自己写错过四次（期望值、ASCII vs 数字、`.mjs` 里写 TS 语法、被查询混合污染的冷热对比），每次都先怀疑被测物。
③ 顺带一条：**观测能力是排障的前置条件** —— CI 日志要登录才能读，于是给工作流加了"失败即注解"，一条命令拿到真因。

## Q. 质量抽检（夜里顺手做的，四个可动手的问题）

转写流水线整夜在跑（常驻 6 GB 显存、内存只剩几百 MB），所以抽检做成**只读、秒级**的
（详见 [QA.md](QA.md)），不去跟它抢资源。量出来的四类问题：

| # | 问题 | 数量 | 该怎么办 |
|---|---|---|---|
| 1 | **碎片谱**（<20 音，有原图却只转出几个音） | **15 份** | 真数据损失 —— 已挂看护，等显存空了自动重转 |
| 2 | **归组重复**（大小写/标点差异被拆成多个组） | 原 **23 个组名 / 46 组** → 现 **0** | ✅ 已落实：`build_web_data.py` 的归组归一化**默认开**（`JP_GROUP_NORM=0` 可回旧口径）。实测 8625→8602 组、同名拆组 **23→0**、音符/变音/id 完全一致 |
| 3 | **标题互相包含**（爬虫把速度/情绪标注拼进曲名） | **187 组** | 喂给 `jp_refine_titles` / `jp_tidy_titles` |
| 4 | **标题无关**（占位名如 `未命名…`/`谱`/`改编歌曲`，而旋律是对的） | **182 组** | 同上；这类"旋律对、标题错"最该修 |

配套工具（都已挂进夜间自检与 CI）：`qa_night_sweep.py`、`triage_fragments.py`、
`check_dup_groups.mjs`、`check_dup_melody.mjs`。

## R. 召回评测：两个口径的差异**量出来了**

| | 离线（Python） | 产品（TypeScript，上线那份） |
|---|---|---|
| rank 规则 | 同代价时**把目标排最前** | 用**上线的并列裁决** |
| 含义 | **召回上限**（能不能找到） | **产品真实名次**（用户看到排第几） |
| L=11 无错音 | **100.0%**（409/409） | 并列乐观 **100.0%** / 产品裁决 **93.7%** |
| 同代价组均值 | 1.72 | 1.7 |

两列在同一 rank 规则下**逐项吻合** —— 证据表明**差距全部来自并列策略，匹配能力两边都是 100%**。
产品口径的完整曲线（`bench_final100`，82 首 × 3 窗口 = 246 次查询）：
L=7 **34.1%**（同代价 **19.6** 组）· L=11 **90.7%** · **L=15 97.6% / Top-3 100%**。
**短查询的瓶颈是并列，不是匹配** —— 这就是前端"这句不是唯一命中"提示的依据。

## 过程中的修正（都记录在提交信息与文档里）

1. **删模型时删多了** ✗：`Qwen2.5-VL-3B`（27 个诊断脚本的默认模型，**已补回**）、`jianpu-lora-v15` 等 LoRA 与 `qwen-mt-v1` 的 heads（**自训产物、无备份**，只能重训）。教训：判断能不能删要查**谁引用它**，不能只看文档怎么描述它。
2. **B 阶段给 Pages 工作流加了 `npm run typecheck` 却没加 `npm ci`** → CI 红；本地一直绿（有 `node_modules`）。
3. **`check_page.mjs` 把 URL 当旋律查询** → CI 只有 node22 红；本机怎么都复现不出（因为我有时不带参数跑）。
4. **测试依赖运行环境语言**（`navigator.language`）→ 本机 `ja-JP` 回落中文所以绿，CI `en-US` 渲英文标签所以红。
5. **`__heap_base` 当函数声明** → wasm 连实例化都过不去（它是 global，不是函数）。
