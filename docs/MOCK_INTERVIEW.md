# 面试演练稿：把这段经历讲成"能扛追问"的样子

> 用法：先背 **①自我介绍** 和 **⑥数字速查**；②③④ 是"会被追问的地方"，每条都指向仓库里的证据 ——
> 被追问时**别背结论，讲怎么验证的**。所有数字都是**实测**（跑法写在最后）。

---

## ① 30 秒自我介绍（照这个节奏说）

> 我维护一个"哼几个音就能查到简谱"的检索站：**11,495 首、253 万音符**的语料，
> **检索整个跑在浏览器里** —— 索引 5.12 MB gzip 到 31 MB 明文，打开到能用约 200 ms，查询中位 **106 ms**；
> 写路径是"边缘反代 + 本机提交"的混合架构。最近把技术栈整体现代化了一遍：
> 前端三件与边缘 Worker 全量 TypeScript（esbuild 只做类型擦除、零运行时依赖），
> 本机写服务搬到 FastAPI + Pydantic v2（自动 OpenAPI，旧服务并存灰度，**21 条请求 × 三种鉴权对拍一致**），
> 加了 Prometheus `/metrics`、ruff/mypy 门槛、pre-commit 与 CI 三矩阵（含 **docker build** —— 我这台机器没装 Docker，镜像可构建性由 CI 证明）。
> 性能上做了两轮：先修排序比较器（**144.6 → 105.9 ms**），再做 ngram 剪枝（长查询 **再降 30%**）；
> 中间还完整试了一次 **Rust→Wasm**，用对拍证明它正确、再用实测**否决**它（端到端 0.84×）。

## ② 会被追问的技术问题（10 条，含"怎么验证"）

| 问题 | 回答要点 | 证据在哪 |
|---|---|---|
| 为什么检索放浏览器跑？ | 语料是**静态**的（追加为主、不改历史），索引 5 MB gzip；放前端 = 零后端成本、零延迟、离线可用、也不会因为后端挂了就不能查 | `ARCHITECTURE.md` 瓶颈表 |
| 11,495 首全扫一遍怎么可能只要 100 ms？ | 不是"每首每位置都算"：每段查询只跟**同一归组**的版本比，且窗口扫到代价已超过当前最优就**早退**；平均每首 220 音符，查询 5–15 音 | `search.ts` 的 `bestWindow` 注释 |
| 剪枝凭什么说安全？ | 代价 0 要求音级 + 变音都对上 → 音级子串必然包含查询串 → **所有代价 0 的歌都在候选集里**（候选是超集）；且只有"代价 0 的结果够填满榜单"时才用剪枝结果 —— 代价 >0 的永远排在后面，挤不进前 N | `search.ts` 剪枝注释 + `check_prune_parity.mjs` |
| 怎么证明剪枝没改变结果？ | 60 条查询（含**模糊**与**多段**）跑"开/关剪枝"两遍，**逐条比对最终卡片**（组/代价/位置/精确计数/段落） | `node tools/check_prune_parity.mjs 60` |
| 为什么 Wasm 方案被否决？ | 内层确实快 3–5 倍（12–39 ms vs 35–143 ms），但**端到端 0.84×** —— 它替换掉的那部分只占小头。数据在手，所以不上线（代码与对拍留在仓库） | `tools/bench_wasm.mjs` |
| 那真瓶颈在哪？ | 排序比较器里每次比较都现算"版本数"（内部 `new Set`）→ `O(n log n)` 次分配。改成每个候选算一次排序键 → **-27%** | 提交 `perf(search): 排序键预计算` |
| 两个后端怎么保证口径一样？ | **不重写**：FastAPI 直接调用原 `server.py` 的业务函数；再跑**对拍矩阵**（21 条请求 × 无口令/错口令/对口令）逐字节比对响应 | `tools/check_parity_legacy_vs_fastapi.py` |
| 灰度怎么切的？ | 同一路径挂两个实现（`--impl fastapi|legacy`），隧道先指新实现，对拍通过后才切；线上真投稿成功留档；随时可退回 | `DEPLOY.md` |
| 监控怎么做的？ | 指标用**归一化路径模板**（1.1 万谱页直接打标签会炸掉时间序列基数）；语料规模用带 TTL 的 gauge；`/api/health` 报 `upstreamOk` —— **只报 `api:true` 会骗人**（服务活着但上游不通） | `app/api.py` + `metrics` |
| 怎么保证文档里的数字不是编的？ | `check_docs_numbers.py` 让四份文档里的曲数/音符数/小节线数**必须等于语料实测**，不一致就红；徽章 URL 也解析进来一起查 | 该脚本 + CI |

## ③ 陷阱题（"你踩过什么坑"）—— 用真事，别用套路

1. **"本地一直绿，CI 却红"**：给 Pages 工作流加了 `npm run typecheck` 却忘了 `npm ci` → CI 里没有 `tsc`。
   我本地怎么都复现不出（因为我有 `node_modules`）→ 把 `node_modules` 移开才复现。
   **教训**：本地绿 ≠ CI 绿，差别就是依赖从哪来。
2. **"测试依赖了运行环境语言"**：UI 语言从 `navigator.language` 推，我本机 `ja-JP` 回落中文所以绿，
   CI 的 `en-US` 渲染出英文标签所以红。**教训**：测试要钉死 locale，别依赖环境。
3. **"删东西删多了"**：清磁盘时删了一个自训模型目录，它只有几 MB，却压着 **27 个**诊断脚本。
   **教训**：判断能不能删要查**谁引用它**，不能只看文档怎么描述它；自训产物没有公开源，删了就没了。
4. **"修复只堵了一半"**：修"缺失资源返回 200 + HTML"这个 bug 时，我先按路径前缀挡（被 URL 规范化绕过）、
   再加"带扩展名"规则（又被无扩展名的 `../etc/passwd` 绕过），第三次才改成**原则**：
   SPA 兜底只对页面路由生效。**教训**：补丁式白名单会一直漏，找到原则才收敛。
5. **"我自己的测试骗了我"**：对拍脚本里拿数字 `1-7` 去比 ASCII 字符，复算出的代价恒等于 `4×音数`，
   看起来像"口径漂了"，其实是测试写错。**教训**：先怀疑测试装置 —— 我这一项上错了三次。

## ④ 规模追问（"如果……你怎么办"）—— 5 条，答案都在架构文档里

| 追问 | 回答骨架 |
|---|---|
| **语料涨到 100 万首呢？** | 索引会到 100 MB+，**不能再整份下发**。改成三层：① 热门子集（按访问量）全量下发、离线可查；② 长尾按需拉**分片索引**（按 group 哈希分片，只拉命中的片）；③ 服务端保留完整倒排做兜底召回。剪枝那条路已经具备（候选只占全库 0.01%–6.8%），只是把"库"从内存挪到网络 |
| **"哼唱"这种模糊查询怎么办？** | 现在靠代价表（音级 + 变音 + 模糊惩罚）已经能容忍少量错音；再往上要走**embedding + ANN**（把旋律片段编码成向量，近似最近邻召回候选，再用精确代价表复核）—— 分工和现在一样：**召回宽松、裁决严格** |
| **下一档延迟瓶颈在哪？** | 不在匹配，在**组内裁决与结果组装**（排序/去重/取 top）。下一步是把 `versions/pop/hot` 这类**按组预计算**进索引（现在每个查询现算），以及让倒排直接吐出"候选组列表"而不是候选歌 |
| **写路径怎么做到高可用？** | 现在刻意是"边缘反代 + 本机隧道"：**零服务器成本**、数据直接落本地 git（可审计、可回滚），代价是**单点**。要真高可用就把写操作改成"边缘收下 → 队列/KV 落盘 → 本机按需消费"，前端只承诺"已受理"，用可观测性（成功率、积压）代替强同步 |
| **成本会怎么变？** | 现在在 Cloudflare 免费额度内（静态资产走 CDN 缓存、只有少量 API 调用）。量大了要盯两件事：**出口流量**（索引走资产的 CDN 缓存而不是每次回源）与 **KV/D1 的读写次数**（把统计类查询缓存起来）。这也是为什么索引放资产层、而不是放在数据库后面 |

## ⑤ 被问倒时怎么办（这题本身也常考）

* **不要编**。说"这块我没实测过，但我会这样验证：…"，然后给出**可执行的验证路径**
  （跑哪个脚本、看哪个数、预期看到什么）。这轮我修 404 时就是靠"先量一量线上到底返回什么"才定位到根因。
* 承认边界：比如"Docker 镜像我没法在本地跑（机器没装 Docker），所以我把它做成 CI 的一个 job —— 可构建性由 CI 证明"。
  这类回答比硬说"我 Docker 很熟"更可信。
