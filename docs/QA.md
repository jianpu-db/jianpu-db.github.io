# 质量工程：自检怎么跑、怎么判、什么时候不能跑

> 一句话：**抽检要抽用户看得见的那一类，而且不能跟生产抢资源。**

## 六条工具（都在本仓库或工具仓库 `tools/` 下）

| 命令 | 干什么 | 代价 |
|---|---|---|
| `py -3.13 tools/qa_night_sweep.py [--json] [--lists DIR]` | 夜间轻量抽检：语料↔索引一致性、曲名后缀、空名/缺 source、碎片谱、低置信度、同名多版本、**近 24 小时新增（git 历史）** | **0.5 s**，只读 |
| `py -3.13 tools/triage_fragments.py [--in] [--out] [--redo-out]` | 把碎片谱按**证据**分类：原图 ≥2 张（多页只转第一页）/ sidecar 有丢页 / 本来就是短曲 / 原图已不在；并生成 `transcribe_source.py` 能直接吃的重转名单 | 秒级，只读 |
| `node tools/check_dup_groups.mjs [映射表路径]` | 查"归组名剥后缀+去标点+转小写后同名、却被拆成多个组"—— 用户可见的重复 | 秒级，只读 |
| `node tools/check_dup_melody.mjs [明细路径]` | 按 (音级串, 变音串) 精确指纹找**重复旋律**，并分成"同曲名/标题互含/标题无关"三类 | 秒级，只读 |
| `node tools/check_recall.mjs [基准] [L] [错音] [窗口数]` | 前端口径召回评测（跑**上线的 search.ts**），同时给 strict / 并列下界 / **并列乐观**三列 | 约 30 s |
| `node tools/qa_snapshot.mjs [--out X.json] [--compare X.json]` | **改动影响对比**：把索引级质量指标（组数/同名拆组/重复旋律/标题互含/占位名）存快照，改完再算一次看每项涨跌 | 秒级，只读 |
| `node tools/audit_deeplinks.mjs [样本数] [站点]` | **线上深链抽样审计**：sitemap 里随机抽样，验 200 + SPA 外壳 + 边缘注入标题；按**站点**分层 | 1–2 s/条 |

## 为什么这样设计（都是踩出来的）

1. **不跟生产抢资源**：夜里转写流水线在跑（显存 6 GB+ 常驻、内存只剩几百 MB）。
   抽检若解析全部曲谱就会拖垮它 —— 所以只读 `data.jsonl` 与站点索引，秒级出结论。
2. **判据用产物里的证据，不靠猜**：
   * "碎片谱"看**原图张数**，不是看音符数就觉得"肯定错了"（本来就短的儿歌也是 <20 音）；
   * "归组重复"看索引里归一化后的键，而不是看曲名"像不像一样"。
3. **不跟流水线的重建打架**：改归组口径要重建索引，而流水线自己也有"空闲重建" —— 撞上就是写冲突。
   所以这类改动**排到流水线空闲之后**（或人工窗口）。
4. **凡是手搓的都出错**（我错了三次：手搓路径、手抽名单、手拼字符串）→
   清单/映射/名单一律 `--lists` / `--redo-out` / `--out` 让**工具产出**，人只审查。
5. **改之前先在内存里原型验证**：归一化只该动组名，于是拿 7 条旋律查询比"代价/位置/精确计数"
   逐条是否不变 —— 不变才敢去改索引构建。

## 一次真跑的结果（2026-10-02 夜）

* 语料 **11,495 首 / 2,532,332 音符**；站点索引 11,495 行 **✓ 一致**；近 24 小时（git 历史）新增 **236 份**；
* 曲名带站名/分类后缀 **202**、空曲名 **0**、缺 source **38**、碎片谱 **80**、低置信度 **162**、同名最多 19 版；
* 碎片谱分类：**多页未转全 15**（真该重转，例:《爱错》原图 4 张 → 只转出 6 个音）、找不到原图 59、本来就是短曲 6；
* 归组重复：**23 个组名 / 46 个组**（`Amani`/`AMANI`、`Love`/`love`、`中国_中国`/`中国，中国`…）。

## 精确重复旋律（同日更晚加的一条）

`node tools/check_dup_melody.mjs [明细路径]` —— 对每首歌的 **(音级串, 变音串)** 做精确指纹并分组。
只报"完全相同"的：移调（同曲不同调）不算，那要先做调性归一才敢说。

实测（11,495 行）：**1,023 组精确重复，牵涉 2,128 行（18.5%）**。分三类，用途完全不同：

| 类别 | 组数 | 是什么 | 该怎么办 |
|---|---|---|---|
| 同曲名 / 不同源 | **654** | 同一首被不同 source 转过（或同一 source 重复登记） | 排名时"按 source 去重版本"那条**已经**把它按一份算 —— 不用动 |
| **标题互相包含** | **187** | 爬虫把**速度/情绪标注**拼进了曲名：`1=F4_4_深` / `牧羊姑娘` / `牧羊姑娘1=F4_4_深情悠扬地` | 喂给 `jp_refine_titles` / `jp_tidy_titles` 做标题归一化 |
| **标题无关** | **182** | 一堆是**占位名**（`未命名jianpujia314236`、`谱`、`改编歌曲`）而旋律是对的 | 同上；这类"旋律对、标题错"最值得修 —— 用户按歌名搜不到 |

分类明细（含每组的曲名与 source）写在 `_analysis/dup_melody.txt`。
夜间自检 `night_qa.cmd` 已把它作为第 4 步（**报告，不设门槛** —— 标题归一化是产品决策）。

> 为什么只出报告不动手：改标题会动到语料与已有评测口径，而且用户那边本来就有两个专门做标题的任务
> （`jp_refine_titles` / `jp_tidy_titles`）。抽检的职责是**把证据摆出来**，不是替它做决定。

## 召回评测：两种口径的差异**量出来了**，全部来自"并列策略"

检索质量有两套评测。第一版我在文档里写成"两边互证" —— 这是**说重了** ✗：
离线口径 L=11 报 100%、产品口径只报 90.7%，两者差 9 个百分点。于是我去**量**这个差（而不是猜），
结论很干净：**匹配能力两边完全一样（召回 100%），差的那 9 个点全部来自"同代价时怎么排名"**。

| | 离线（Python） | 产品（TypeScript，上线那份） |
|---|---|---|
| 工具 | `jianpu2/tools/melody_retrieval_eval.py` | `tools/check_recall.mjs` |
| rank 规则 | 同代价时**把目标歌排最前** | 用**上线的并列裁决**（证据优先/置信度/版本数/段落权…） |
| 这是什么 | **召回上限**（"能不能找到"） | **产品真实名次**（"用户看到排第几"） |
| L=11 无错音 | **Top-1 100.0%**（409/409） | 并列乐观 **100.0%** / 产品裁决 **93.7%** |
| 同代价组均值 | **1.72** | **1.7** |

两列在**同一个 rank 规则**下逐项吻合（100.0% vs 100.0%、1.7 vs 1.72）——
这就是"差异来自并列策略"的证据。`tools/check_recall.mjs` 现在同时打印三列：
`strict`（产品裁决）、`并列下界`（最保守）、`并列乐观`（= 离线口径，用来和离线对照）。

### 完整曲线（产品口径，`bench_final100`，82 首 × 每首 3 窗口 = 246 次查询）

| 查询长度 | strict Top-1 | Top-3 | Top-5 | 同代价组均值 |
|---|---|---|---|---|
| L=7 | 34.1% | 56.1% | 67.5% | **19.6** |
| L=11 | 90.7% | 99.6% | 99.6% | 1.4 |
| L=15 | **97.6%** | **100%** | **100%** | 1.0 |

**最有用的一行是"同代价组均值"**：L=7 时有 **19.6** 组并列 —— 说明短查询的瓶颈
**不是匹配不够好，而是本来就有很多歌共享同一小段音**。这正是前端"这句不是唯一命中"提示的依据，
也是"别用 Top-1 单一指标吹检索质量"的理由。

### 注入错音（模拟凭耳朵记错）

L=11 错 2 个音：strict Top-1 50.0% / Top-3 74.0% / Top-5 80.9%（同代价组均值 5.0）。
代价表刻意**允许**少量错音（违反单调性的惩罚），所以召回还在，但名次明显变差 ——
这也是为什么界面上同时给"代价"和"并列数"，而不是只给一个名次。

### 为什么必须补产品口径那套

离线评测验不到 TS 侧 —— 剪枝最坏的情况就是"把目标歌剪掉"，离线口径根本看不出来。
主口径引用产品口径的数字；离线口径只在"召回上限/跨版本对照"时引用。

## 还该知道的两件"坑"

* `data.jsonl` 里 `file` / `source` 是 **list**，而站点索引里是**字符串** —— 两边形状不同，别混用；
* "近 24 小时新增"**不能用文件 mtime 统计**：流水线重建会刷新整目录 mtime，
  第一版算出 23,982 份（而 `scores/` 一共才 24,011 份）。要用 `git log --since=24.hours --name-only`。

## 用快照验证过一次真实改动（归组归一化开关）

```
node tools/qa_snapshot.mjs --out before.json
JP_GROUP_NORM=1 py -3.13 tools/build_web_data.py     # 开开关重建
node tools/qa_snapshot.mjs --compare before.json
```

| 指标 | 关闭（现状） | 开启 |
|---|---|---|
| 组数 | 8625 | **8602（-23）** ✓ |
| **同名拆组** | **23** | **0** ✓（彻底消除） |
| 标题互含 | 187 | **184（-3）** ✓（合并组的顺带好处） |
| 重复旋律 / 占位名 | 1023 / 233 | 不变 ✓（**无副作用**） |

这就是"改动影响对比"该有的样子：**每一项涨跌都看得见**，而不是"感觉好多了"。
`--compare` 会把变差的项标成 ✗（"越少越好"与"越多越好"的指标方向在脚本里分开定义）。

## 守卫矩阵：哪条检查在哪个环节跑（以及为什么不换个位置）

| 检查 | CI | 夜间 | 手动/审计 | 为什么在这儿 |
|---|:--:|:--:|:--:|---|
| `check_search` · `check_ui` · `check_page` · `check_jptok_js` · `check_og_meta` | ✅ | | | 纯本地、秒级、无外部依赖 → 每次都该跑 |
| **`check_ranking_golden`**（12 条金标准） | ✅ | | | **排名质量必须每次挡**；用例答案客观（查询取自目标歌自己的谱） |
| **`check_worker_routes`**（23 项） | ✅ | | | 直接 import Worker + 假 ASSETS；**本地静态服务走不到 SPA 兜底**，只能这样测 |
| **`check_prune_parity`**（开/关剪枝逐条对比） | ✅ | | | 剪枝最坏是"把目标剪掉"，必须有等价性锁 |
| **`check_wasm_parity`**（逐首 + 端到端） | ✅ | | | 跨仓库产物，缺了就**明确跳过**（CI 里没有工具仓库） |
| `bench_search`（性能趋势） | ✅ | | | 只打印数字、不设阈值（机器差异大，硬卡会误红） |
| `check_parity_legacy_vs_fastapi`（21×3 对拍） | ✅ | | | 在 python 矩阵里跑；需要起两个后端 |
| `lint_python`（ruff+mypy） · `check_docs_numbers` | ✅ | | | 门槛类，必须每次挡 |
| **`qa_night_sweep`** + `triage_fragments` | | ✅ | | 需要**最新语料**（流水线夜里在写）→ 放夜间；只读、秒级、不抢 GPU |
| **`check_dup_groups`** · **`check_dup_melody`** | | ✅ | | 是**报告不是门槛**（"用户可见的重复"属产品决策）→ 只出证据 |
| **`check_recall`**（前端口径召回） | | | ✅ | 基准集在**工具仓库**、跑一次约 30 s；CI 里没有那份名单 |
| **`audit_deeplinks`**（线上抽样） | | | ✅ | 要打**线上网络**、且是抽样 → 审计用途 |
| **`qa_snapshot`**（改动影响对比） | | | ✅ | 用法是"改前存一份、改后比一次"→ 人为触发，不是定时 |

**判据**：*能本地跑完的进 CI；需要最新语料或只出报告的进夜间；要网络 / 跨仓库 / 人为对比的留手动。*
任何一条"本该进 CI 却没进"的，都应该能在这张表里找到理由 —— **找不到理由就是漏了**。
